# StudyFlow Architecture

## Goal

A small, single-user study planner. Students create tasks with a subject and priority, filter tasks by status, subject, and priority, mark tasks complete, and delete tasks. There is no sign-in.

## Features

- Create a task with a title, subject, and priority.
- Filter by all/pending/completed status, subject, and priority.
- Mark a task complete or delete it.
- See loading, empty, success, and error states.

## Simple MERN architecture

```text
React (Vite browser app)
       | HTTP / JSON
       v
Express (REST API)
       | Mongoose
       v
MongoDB
```

- **React** displays the form and task lists and sends requests to the API.
- **Express** validates requests and defines the API routes.
- **Mongoose** validates and stores task documents.
- **MongoDB** persists tasks between app restarts.

The repository has a `client` folder for React and a `server` folder for Express. The root npm scripts start both during development. The backend follows MVC: Mongoose models define data, controllers handle task logic, and routes connect URLs to controller functions. Express setup, database configuration, and error middleware are kept separate.

## Folder structure

```text
client/src/
       components/
              ComponentName/
                     ComponentName.jsx
                     ComponentName.css
       services/          API requests
       utils/             small formatting helpers
server/src/
       config/            database connection
       controllers/       request logic
       middleware/        error handling
       models/            Mongoose schemas
       routes/            API route definitions
       app.js             Express middleware and route setup
       server.js          database connection and HTTP startup
```

## Data structure

MongoDB collection: `tasks`. Each task document contains:

| Field | Type | Rules |
| --- | --- | --- |
| `_id` | MongoDB ObjectId | Generated by MongoDB; used as the task ID |
| `title` | string | Required and trimmed |
| `subject` | string | One of `DBMS`, `DSA`, `Mathematics`, `AI/ML`, `Web Development`, or `Other` |
| `priority` | string | `Low`, `Medium`, or `High` |
| `completed` | boolean | Defaults to `false` |
| `createdAt`, `updatedAt` | date | Managed by Mongoose timestamps |

Completion is a boolean rather than a separate status field: `false` means pending and `true` means completed. Priority is a fixed set of three values, so a dropdown is simpler and more reliable than free text.

## API

All routes use JSON and are prefixed with `/api`.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/health` | Check that the API is running |
| `GET` | `/api/tasks` | List all tasks, newest first |
| `GET` | `/api/tasks?completed=false` | Filter by completion; also accepts `priority` and `subject` |
| `POST` | `/api/tasks` | Create a task; completion defaults to `false` |
| `PUT` | `/api/tasks/:id/complete` | Mark a task complete |
| `DELETE` | `/api/tasks/:id` | Delete a task |

Unsupported filter values and invalid input return `400`; malformed IDs return `400`; unknown task IDs return `404`; unexpected errors return `500` without exposing a stack trace.

## Request flow

1. The student submits the React form. The browser checks the title, subject, and priority.
2. React sends a JSON `POST /api/tasks` request.
3. Express checks the request and Mongoose enforces the document rules before saving to MongoDB.
4. The API responds with the saved task. React refreshes its task list and shows a success message.
5. The student can filter the list, mark a task complete with `PUT /api/tasks/:id/complete`, or delete it with `DELETE /api/tasks/:id`.

Validation belongs on both the client and server. Browser validation improves the experience, but server-side validation is still required because API requests can come from outside the UI.

## Edge cases to handle

- Task title is empty or only whitespace.
- Subject is missing or unsupported; priority is missing or unsupported.
- A task ID is malformed or refers to a task that does not exist.
- There are no tasks in one of the views.
- The API is unavailable or a request fails; show an error and let the student retry.
- The submit button is used repeatedly while a save is already in progress; disable it during submission.
- A completed task must not remain in the pending view after the API confirms completion.
- The database is not configured or cannot be reached; explain how to set `MONGODB_URI` rather than silently losing tasks.

## Local configuration

The server reads `MONGODB_URI` and `PORT` from `server/.env`. The client may set `VITE_API_URL` in `client/.env` if the API is not at its default local URL. Start from the checked-in `.env.example` files and never put real credentials in source control.

For development, MongoDB Atlas or a local MongoDB Community Server can be used. On Render, configure `CLIENT_ORIGIN` with the frontend origin and `VITE_API_URL` with the backend URL ending in `/api`.
